# 已接受正文的派生资料管线与恢复

## 2026-08-26 历史正文恢复读取增量

恢复已有版本继续以当前章节版本为父版本，原子追加新的 “recovery” 不可变版本并更新章节当前引用；旧版本不覆盖、不删除。编辑器重开时从章节当前版本沿父引用反向校验到第 1 版，而不是要求所有历史行构成唯一全表线性序列。只有不属于当前权威链且自身可安全识别的记录可以保留并隔离；当前版本缺失、跨范围、正文或校验和不一致、父链缺失／循环、序列不连续时仍停止正文写入。

较早恢复稿仍是作者资料：它不会自动替换当前正文，也不会因为基线较旧而把整个页面变成永久冲突。稳定正文通过校验后正常打开，同时展示较早稿与当前稿供作者明确处理。当前真实文件 SQLite 回归已经覆盖恢复第 1 版、关闭数据库、重新打开及三版父链守恒；现场 v0.2.12 数据库和对应坏行未取得，不能把构造触发写成现场唯一根因。

## 2026-08-22 结果隔离、持久责任与统一前检增量

直接模式和专业模式共用隔离与版本安全：所有生成结果先保持隔离，每次远程发送逐次披露，作者明确选择“使用这版”后才写入或替换正文并创建不可变版本；失败、取消、模式或基线变化都保持正文不变。附件提出的一次点击远程授权和自动写正文仍待独立授权，不属于当前完成能力。

本轮新增统一的接受章节后事实前检，覆盖编辑器、导入、从想法创建、后台任务和版本恢复等入口。确定性本地整理只读取已保存版本、持久责任字段和精确正文证据，不在任务执行时读取当前界面模式；派生失败不回滚正文。重开后的撤销入口从当前不可变版本、已接受记录和基线版本重建。当前工作树全量持久化回归和原生层检查已通过；真实安装程序中的备份恢复、关闭重开与进程中止仍待验证。

## 1. 触发范围

以下动作都围绕稳定正文版本登记同一类本地任务；Candidate 的生产 SQLite 路径在同一事务提交版本与任务，其他来源按后文已实现边界处理
`story.accepted-version.process`：

- 编辑器接受 AI 建议版本：`candidate_accept`；
- 导入改写中接受代表段落或逐章建议：`chapter_import`；
- 编辑器或导入流程追加式恢复历史原文：`version_restore`；
- 用户明确点击保存正文：`manual_save`。手动保存只更新本地搜索和故事关联；自动保存不进入这条
  管线，也不会调用模型。

任务元数据只保存项目、章节、稳定版本、触发来源、字符数、四个阶段开关、
organizeLocalStoryFacts 持久责任字段，以及阶段补缺任务所需的幂等键、规则版本和代数，不保存
正文、Prompt、API Key、模型回复或错误原文。这个布尔值在接受或保存决定时确定，并同时保存在新章节
版本；缺失它的旧版本、旧调用方或旧任务一律按 false 处理，不根据 worker 重启时的直接/专业模式猜测。
任务创建、严格匹配、人工重试和 worker 恢复都保留同一个值。任务使用稳定版本 ID 作为幂等键，同一个
版本不会重复登记不同工作；新任务仍把两个 Provider 阶段显式保存为 false，旧 Provider 开关继续归一为
本地范围。

### 1.1 Candidate 接受的零云调用合同

所有 `story.accepted-version.process` 来源都通过同一 local-only 输入合同。该输入将任务硬锁为本地搜索
和本地因果投影，并在登记、执行、人工重试和 worker 启动恢复四个边界强制关闭章节摘要与连续故事
状态模型阶段。即使旧队列元数据把这两项写为 `true`，新代码也只按本地范围恢复，不发送正文。

生产 SQLite 中，Candidate 接受的单个本地事务只允许：

1. 把用户实际看过的 Candidate 写入正式正文；
2. 新建带持久本地整理责任的不可变版本，保留旧版本；
3. 提交 Candidate 决定和可追溯链；
4. 通过同一事务内的任务工厂登记可重建、无需 Provider 的本地任务。

因此正文、版本、Candidate 决定或任务创建任一写入失败时，Candidate 接受事务整体失败，不会留下
“正文已提交但没有恢复任务”的半状态。该原子任务边界当前可由生产 SQLite 的 Candidate 接受路径证明；
手动保存、导入、历史恢复等其他来源仍只按各自已实现边界记录，不在本文扩写成全部原子登记完成。

本地搜索或因果投影失败只作为可重建派生失败，不得回滚已接受正文或新版本。Model Hub 中
配置了连接不等于授权处理正文。生产页保留的逐章云端摘要/故事识别按钮当前为禁用态，并解释未来动作
必须事前展示发送范围、Provider、精确模型、费用或价格未知、调用次数和重试上限，再取得单独确认。
在这个独立状态机具备持久发送边界、私密 fail-closed、取消和 ambiguous 防重发前，按钮不会 dispatch。

### 1.2 前台接受与后台派生的等待边界

编辑器点击“使用这版”后，前台只等待以下核心权威完成：正文替换围栏、AI 建议草稿修订比较、
章节修订比较、新不可变版本创建和建议草稿终态。提交成功后，页面立即读取并显示新正文、当前版本
和已使用状态；版本反馈、任务登记后的执行和派生反馈在后台继续。

因此，后台搜索、故事关联或设定整理变慢、失败或等待重试时：

- 不把“使用这版”继续显示为数据库事务仍在进行；
- 不回滚正文、新版本或建议草稿决定；
- 不发起模型调用；
- 任务中心显示可重建失败或后续状态，重启从持久状态幂等对账。

如果核心提交失败，AI 建议草稿继续隔离，正文和当前版本保持原值；如果提交结果无法确认，页面
不得把它猜成成功或明确失败，而应重新读取权威状态并显示“结果待核对”。重复点击仍受建议草稿和
章节修订比较保护，一次决定最多产生一个新不可变版本。

## 2. 执行顺序

`accepted-chapter-pipeline.ts` 当前只执行两个互相独立、无需 Provider 的可重建阶段：

1. 更新本地搜索；
2. 只从合格事实重建故事关联。

所有来源都只运行这两项。任何派生阶段失败都不会回滚已接受正文；`waiting_retry` 也只重试本地阶段。
旧 Provider-only 补充任务到期后终结为取消，不建立新 invocation，也不会因为重启自动发送。

绑定版本已经不是当前版本、版本不存在或本地权威来源变化等终态不进入重试，只结清当前任务所绑定的
不可变版本。旧自动摘要偏好会在页面加载时退役为关闭，不能重新激活云端阶段。

### 2.1 历史连续故事状态回执

已有故事变化记录对每条历史 Model Hub 路由使用项目、章节、不可变版本和任务组成的持久唯一键。历史实现派发前
先读取 `continuous_story_state_route_receipts`；已有回执时直接返回已完成，`force`、进程重启或 worker
恢复都不会再次发送正文。当前后台管线不再创建新的路由工作；这些表只用于读取和审计既有结果。

SQLite 提交会再次校验章节仍活跃、绑定版本仍为当前版本且正文 SHA-256 未变化，然后在同一事务中：

1. 退休相同实体、事实类型和替换键的旧系统临时投影并追加修订；
2. 写入本次合法 StoryFact 与初始修订；
3. 最后写入包含供应商、模型、调用 ID 和候选计数的完成回执。

任一步失败会整体回滚，旧投影不会只退役一半，回执也不会领先于事实。浏览器开发存储通过一次
`localStorage` mutation 提交同等状态。`0052_continuous_story_state_route_receipts.sql` / Tauri `55`
只向前增加该表和来源门禁；`0055_continuous_story_state_historical_route_receipts.sql` / Tauri `58`
允许同项目、章节、不可变版本与内容哈希全部匹配的历史回执随一致性备份恢复，而新提交仍要求当前
版本 CAS。删除作品时回执可随作品级联清理，不阻断正常删除。

## 3. 自动恢复与人工恢复

桌面 Tauri 运行时启动 `AcceptedChapterPipelineWorker`：

- 启动后立即检查一次，之后每 15 秒检查；
- 只执行已到期的重试，或超过 30 秒仍未被前台接手的排队任务；
- 同一进程中的重叠轮询合并为一次；
- 单条损坏或发生竞争的任务不会阻止其他任务；
- 使用独立的到期任务查询按最早到期顺序分页；单轮最多扫描 1,000 条、处理 200 条，
  不再受任务中心“最近 200 条”展示窗口限制；
- 关闭应用时先停止轮询并等待当前安全边界，再关闭备份运行时和 SQLite。

30 秒宽限避免前台刚接受正文时与后台 worker 争抢同一任务。任务仓库的修订/CAS 和租约仍是
最终并发门禁。扫描和处理上限避免一次启动长期占用前台；游标会在后续轮询继续推进，因此也
不能把单轮上限误解为丢弃更旧任务。

任务中心对合法、可重试且元数据完整的该类任务显示“立即重试后台整理”。点击后不会增加一次
额外尝试计数：失败登记时已经进入下一次尝试，`retryNow` 只把计划时间提前到当前时刻。
元数据不完整、类型不匹配或重试次数耗尽时不会显示伪操作按钮。

立即重试不会把页面刚读到的旧失败范围直接带进执行。`retryNow` 用任务序号、尝试次数和当前
`failure.causeCode` 做同一次 CAS，并把规范阶段处置编码成 `pipeline.retry.v2...` 进度标记；标记只含
阶段代码和尝试次数。前台随后只读回刚排队的任务并精确核对完整元数据、序号、尝试和标记，任何后台
抢先执行、再次失败、删除、替换或损坏都会在四个阶段之前失败关闭，也不会意外创建新任务。若进程恰好
在排队后、执行前退出，worker 重启后从同一持久标记恢复失败、`not_applicable` 与 `deferred` 范围，
不会退化为全阶段重复调用；旧 attempt 的标记不能覆盖新状态。

### 3.1 旧作品当前版本回填

旧作品不会在启动时无声扫描或产生模型费用。用户可在章节整理的高级区域先生成只读本地计划，计划会列出：

- 活跃章节、合格章节、空白章节和不稳定章节数量；
- 已登记与待登记任务数量、涉及字符数；
- 本地搜索和因果投影缺失范围；
- 固定为 0 的 Provider 调用上限。

计划本身不写数据库，也不调用模型。只有用户在看过计划后明确确认，服务才按稳定版本 ID 幂等登记
`historical_backfill` 任务；登记前会重算计划指纹，章节、版本、隐私、任务或项目开关有变化时整批失败
关闭并要求刷新。回填只处理每章当前、非空、内容校验一致的稳定版本，不遍历也不改写旧历史版本；
登记出的新任务把章节摘要与故事状态阶段显式保存为 `false`。

为避免旧书一次占满前台，worker 每轮最多执行 5 个历史回填任务，其余任务留在持久队列供后续轮询。
本地计划不读取模型路由，也不因 Model Hub 已配置而扩大范围。

### 3.2 阶段级补缺与失败恢复（规则 v2）

历史回填不再把“存在同版本任务”等同于本地阶段已经完成。首个任务继续使用已发布的
`story.accepted-version:<versionId>` 幂等键；只有缺失阶段才登记
`story.accepted-version:<versionId>:backfill:v2:<stage>:<generation>` 补充任务。因此无需新增
SQLite 迁移，已有任务和数据库可原样读取：

- 新任务成功时，以规范 outcome 进度证据精确记录本地阶段处置。全完成继续写兼容格式 `pipeline.outcome.<stages>`；包含终态时写紧凑格式 `pipeline.outcome.v2.<stage>-<c|n|d>`；
- `not_applicable` 可作为该版本的覆盖证据，历史回填不会逐代重复补建；
- 旧摘要/故事状态开关和旧 provider failure 不再形成当前待补范围；
- 新任务失败时，安全的 `failure.causeCode` 保存失败阶段掩码；同一任务重试及后续补充任务都跳过已经成功的阶段；
- 同轮同时出现终态/延期与可重试失败时，紧凑 v2 failure evidence 会把失败、`not_applicable`、`deferred` 三组处置一起持久化；普通 progress 在失败转换中被清空也不会丢失处置。最终耗尽后 `c/n` 仍算覆盖，`d` 仍算缺失并等待下一次显式确认；
- 重试耗尽后仍保留阶段掩码；失败或取消的补充任务使用下一代确定性键恢复，不覆盖旧审计记录；
- 无阶段掩码的旧终态失败任务只按当前所需本地阶段保守补缺；
- 排队、运行、等待重试或暂停的阶段视为已经登记，不会并发创建第二条相同工作；历史任务仍受 worker 单轮最多 5 条约束；
- 计划指纹纳入章节/版本/内容/隐私修订、项目开关、任务序列/状态/失败掩码以及补充任务代数，登记前继续执行只读重算和 CAS 防护。
- 每条实际登记前再次核验章节修订、隐私修订、当前版本、正文校验值和任务权威。首次写入前重算已过期时整批返回 `stale` 且零写入；批处理中已有项目登记后再过期则返回保留已登记计数的 `partial`；相同权威任务恰由并发方先写入时计入 `alreadyRegistered`，不误报失败。
- 上述复核是“入队前校验”，不是跨章节库与任务库的原子锁。执行时本地搜索只收录项目当前正文，因果投影只读取当前正式、已确认、未废弃的权威事实。任何阶段都不能回滚或改写已接受正文。
- `runSearch`、`runChapterSummary`、`runStoryState`、`runCausalProjection` 全为 `false` 的空范围任务在直接执行、登记和 worker 恢复三处均失败关闭，不会生成空 outcome。

批量登记现在返回 `completed | partial | stale` 回执。若中途某条登记失败，已创建或并发登记的数量不会丢失；
回执会分别给出尝试、成功登记、新建、并发已登记、失败和剩余任务数，界面显示“部分现有章节任务已登记”，
不会把已经成功的登记误报为“一个都没有登记”。

## 4. ProjectSeed 进入真实续写上下文

三条创建旅程保存的 `ProjectSeed` 不再只是恢复表单。真实续写会读取项目当前 Seed，并只把
作者已确认且非空的字段转换为可追踪上下文：

- 禁止项进入必选硬约束；
- 类型、基调、风格、POV 和改写规则进入当前写作任务；
- 人物和关系进入人物当前状态；
- 世界与创作起点进入世界设定；
- 冲突、当前方向和初步大纲进入场景目标。

未确认的导入分析或 AI 推测不会进入生成上下文。每个采用字段在上下文来源和内容最小化 trace
中保留 `project-seed:<field>` 定位、Seed 修订和是否因 Token 预算舍弃的信息；正文和字段全文
不写入 trace。

## 5. 私密章节与安全边界

私密章节受项目级发送前门禁约束。只要项目仍保留任何 `local_only` 章节（项目归档不会解除保护，
回收站中尚未永久清除的记录也仍受保护），所有可能读取全书事实、因果关系、语义召回或其他章节资料的续写、选区改写、规划、深度
审稿、语义复核、连续提取、导入分析和剧情试演都只允许使用已验证的回环本地模型。远程 Rerank
在读取和发送召回内容前就会禁用。

每次操作先取得只含章节 ID、当前版本、章节修订、隐私修订、状态和隐私模式的 authority 指纹；
真正派发前由原生 SQLite `BEGIN IMMEDIATE` 事务重新读取全项目并精确比较。新增/删除章节、版本变化、
归档/回收状态或隐私变化都会使本次调用在发送 0 字后停止。远程 generation、Embedding 和 Rerank
复核成功后创建不含正文的派发租约，并覆盖完整原生网络生命周期；成功、失败、取消、超时或 panic
真正结束后才释放。租约期间只阻止新增/转入 `local_only` 与项目删除，普通正文编辑、版本提交和
自动保存仍可继续。Renderer SQL bridge 无权读写租约；一致性备份即使物理包含租约，恢复也明确不复制。
默认项目导出不包含私密章节；显式包含是独立用户选择。切换为私密只阻止未来发送，不能声称删除
供应商历史副本。

## 7. 尚未宣称完成
