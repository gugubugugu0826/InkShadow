## 3. D1：本地数据库访问与重载生命周期

### 3.1 原状态时序

1. 一个根事务把共享的“事务活动中”标记设为真。
2. 路由加载、编辑器读取或维护动作从另一条异步链进入。
3. 适配层把这个无关根操作误判为同步嵌套事务并立即失败。
4. 页面把错误投影到持久错误边界；普通重试仍复用同一个原生会话。
5. 桌面网页容器（WebView）重载时，原生进程未退出；孤儿事务或 `restore_source` 恢复附件可能继续留在连接上，错误因此跨路由扩散。

### 3.2 当前修复

- 每个根操作进入先进先出执行队列；只有同一同步调用栈内的真正嵌套仍被拒绝。
- 队列等待、原生命令、事务、提交和回滚均有上限；尚未开始的超时明确为“未开始”，已写或提交后
  无法确认的结果明确为“结果待核对”。超时等待者不会稍后偷偷执行。
- 写入或提交结果无法确认时关闭并使会话失效，避免在不确定连接上继续写。
- 桌面网页容器重载会接管连接、回滚孤儿事务、清除旧恢复附件；清理失败时使连接失效并重新打开。
- 原生诊断保留稳定阶段和脱敏请求标识；普通界面只显示可操作中文，不显示数据库路径、
  数据库查询语句（SQL）、内部码或标识符。
- 不通过无限重试、切换空库或删除本地数据恢复。

### 3.3 真机结果与剩余边界

- 在同一隔离数据库中预置 2 个作品、4 个章节，连续重载 3 次并完整结束、重启进程 2 次；每次页面均可读取。
- 前后数据库完整性正常、外键违规为 0；作品、章节、当前版本、正文长度与正文 SHA-256 逐项不变，
  未扩散到另一作品。
- 外部写锁、维护竞争和无法确认提交的分类由聚焦自动化覆盖；最终安装包上的长时压力矩阵仍待运行。

## 4. D2：接受 AI 建议草稿的原子边界

### 4.1 原状态时序

1. 页面进入“使用这版”，开始正文替换围栏和建议草稿修订比较。
2. 受 D1 连接争用影响，核心事务可能尚未取得执行权；证据数据库未出现正文、当前版本或建议草稿
   状态的部分更新。
3. 即使核心提交完成，页面也可能继续等待版本反馈或可重建派生任务，使按钮看起来仍在事务中。
4. 用户强制结束进程后无法从页面判断是未提交还是提交后派生尚未完成。

### 4.2 当前修复

- 接受事务只做正文替换围栏、建议草稿修订比较、章节修订比较、不可变版本创建和建议草稿终结。
- 一次点击最多创建一个新版本；重复点击使用同一修订权威，不重复应用。
- 核心提交成功后立即更新正文、当前版本和建议草稿状态；版本反馈与已接受版本管线在后台继续。
- 本地搜索、故事关联、设定整理等派生失败只形成可重建失败，不回滚已接受正文。
- 接受阶段模型调用增量严格为 0；失败时建议草稿继续隔离，正文和当前版本不做半更新。

### 4.3 真机结果

- 正常接受与重复点击均只接受一次、只创建一个新不可变版本；旧版本保持不变，接受过程新增模型调用为 0。
- 正常路径正文从 23 字增至 45 字、版本总数从 4 增至 5；重复点击虽然捕获到 2 个界面事件，
  数据库仍只新增同一个版本。
- 核心事务故障时正文、当前版本和 AI 建议草稿均没有半更新；派生管线故障时已接受正文保留，失败任务可重建。
- 事务故障前后数据库 SHA-256 同为
  `12fbf1c4d0aee93bb1e3c38bef0bdfdb9ad35b6420a80b3bb122ff9a51a061ea`；派生失败任务保存为
  “等待再次处理”，尝试序号 2 / 上限 3 表示下一次允许的编号，不代表系统已经自动重试。
- 在接受提交前强制结束进程，重启后仍可读取，正文、当前版本和 AI 建议草稿保持未接受状态。
- 这些结果分别由“接受一次”“无部分写入”“派生失败不回滚”合同核对，不以按钮视觉状态代替数据库证明。
- 主动取消未单独在真机执行，仍由自动化合同覆盖。

## 5. D3：开书三个方案的独立结算

三个方案继续使用稳定槽位和请求标识。每批最多三次明确模型调用，每槽 0 自动重试。

当前批次改为等待三个槽各自结算，而不是任一失败后提前退出：

- 成功槽单独持久化并保留，不因其他槽失败而丢失或重复生成；
- 发送前失败归档为未发送或明确失败；
- 已越过原生发送边界但无法确认结果的槽归档为“结果待核对”；
- 批次结束后再汇总错误，页面分别说明可用、失败和未完成槽；
- 重启读取既有终态或将悬挂记录保守结清，不重新派发已发送或结果待核对的槽。

隔离 Windows Tauri 以同一批三个稳定槽重跑：第 1 槽成功并保留可见结果，第 2 槽收到明确服务失败，
第 3 槽在发送后连接中断并标为“结果待核对”。三个槽各有一次且只有一次模型调用记录，自动重试为 0；
页面重载和完整进程重启后均没有新增发送，成功槽的内容和上下文记录仍可读取。

## 6. D4：自动备份清单第 2 版

### 6.1 状态机

新清单把模糊的“创建中”拆成：

```text
已预留 ├→ 未开始
       └→ 写入中 → 核验中 → 成功
                      ├→ 失败
                      └→ 结果待核对
```

- 从未开始写入：结清为失败/未开始，可由后续明确调度创建新备份。
- 写入或最终安装结果无法确认：标记“结果待核对”，禁止覆盖式盲目重试。
- 只有文件存在、SQLite 完整性/外键/结构、大小和 SHA-256 摘要均通过才标记成功。
- 每次启动检查都复验第 2 版成功项；旧第 1 版“就绪”项先转为成功项，再走同一复验路径。
- 成功文件缺失、字节数或 SHA-256 不符、文件检查异常时，对应项降级为“结果待核对”，
  最近成功时段回退到较旧的已核验健康备份，不对原时段盲目重发，也不删除摘要不符的文件。
- 旧第 1 版“创建中”没有足够阶段证据，只能恢复为“结果待核对”。

### 6.2 原生写入边界

- 单个独立原生命令用独立 SQLite 连接执行 `VACUUM INTO`，不占用编辑器共享执行器，也不使用渲染层
  `ATTACH`。
- 临时文件严格绑定备份标识；核验后使用不覆盖安装语义放到最终目标。
- 最终清单写入无法确认时保留已生成文件并标记“结果待核对”，不盲目覆盖。
- 只有新备份确认成功后才允许按保留策略清理；最新健康备份始终受保护。

## 7. D5：能力验证进入普通调用账本

### 7.1 前向数据迁移

- 数据迁移 `0071_model_capability_probe_invocation_ledger.sql` 对应桌面原生迁移 `74`。
- `model_invocation_facts.task` 新增独立 `capability_probe` 任务，不冒充开书或正文生成。
- `model_capability_scans` 新增可空且唯一的 `model_invocation_id`；触发器要求能力证据只能绑定同一
  模型目录项、状态匹配的终态能力验证调用记录，并禁止事后改绑。
- 迁移前后模型调用记录计数必须一致；已发布迁移和校验和没有改写。
- 这是本轮唯一新增 SQLite 前向迁移。自动备份清单第 2 版是文件清单格式升级，不是 SQLite 迁移。

### 7.2 发送与恢复

- 披露和确认前为 0 条真实调用记录；取消保持 0 次调用。
- 确认后创建一条运行中的能力验证调用记录，包含精确连接、模型、远程/本机去向、费用上限或未知、
  尝试次数 1、自动重试 0。
- 原生网关在网络开始前，以同一个数据库连接原子写入发送时间并核对调用标识、任务、连接、模型、
  范围和修订；核对失败时网络调用为 0。
- 成功、明确失败、取消或结果待核对分别结清同一条记录，保存模型服务明确返回的输入/输出词元、
  缓存词元与费用；模型服务未返回时保存“未知”，不估造。
